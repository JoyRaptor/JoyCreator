## ⚠ READ THIS FIRST — the install watcher is now DEAD, on purpose

The repo had `gradlew.bat -t installDefaultDebug` running as a background continuous build. **Every
successful compile auto-installed onto whatever phone was plugged in.** On 2026-08-04 that pushed a
build onto JoyRaptor's **Note 20 — the phone holding his real 45-minute project** — without anyone
deciding to. It was stopped (the wrapper `cmd.exe` plus the Gradle daemons).

Consequence: **`adb install` is now manual.** If a build "doesn't take", that is why.

```bash
adb -s SANDBOX_SERIAL install -r app/build/outputs/apk/default/debug/app-default-arm64-v8a-debug.apk
```

Restarting the watcher is a bad idea while the Note 20 is ever attached. If you want it back, gate
it on the sandbox serial.

## THE THREE LESSONS (the third is new and cost the most)

0. **Check whether the tool can actually do the thing before declaring it impossible.** "adb
   cannot express hold-then-move" was repeated for a whole session and written into two documents.
   `input draganddrop` does exactly that, and one `input` usage dump would have found it. The cost
   was not a bug — it was work handed to JoyRaptor that the machine could have done.
1. **A green harness is not a working feature.** M11 anchoring shipped with 35 passing checks, a
   debug probe and a confident commit message — and was **completely inert**. Ask "who CALLS this?"
2. **Adversarially review your own fixes.** Five rounds found ~45 defects. Round five found a
   HIGH-severity regression in round four's *fix*.
3. **A fix can be worse than the bug, and the smoke test won't tell you.** The reorder playhead
   restore passed a fraction of the *effective* segment where the consumer wanted a fraction of the
   *full source*. On an untrimmed 1× clip those are identical — so it looked perfect in exactly the
   test a fresh build gets. On any trimmed clip it threw the player to the clip's end. **When two
   quantities coincide on the default case, the default case cannot test them.**

### ⚠ CORRECTION: `adb` CAN drive the hold-then-move gestures — use `input draganddrop`

I claimed all session that `adb` could not test the dislodge because `input swipe` interpolates
movement and cannot hold still first. **That was wrong, and it cost several rounds of "needs
fingers".** `input draganddrop x1 y1 x2 y2 duration` sends DOWN, **waits the long-press timeout**,
then moves, then UP — exactly the gesture. It is present on Android 10 (`input motionevent` is not).

```bash
adb -s SANDBOX_SERIAL shell input draganddrop 694 1832 900 1995 1800
```

## HOW TO WORK HERE

- **`adb -s SANDBOX_SERIAL`** always — a stale offline `emulator-5584` broke bare commands.
- **Device rule: Note 9 `SANDBOX_SERIAL` is the sandbox.** If the Note 20 `REAL_SERIAL` is
  attached, STOP all device work — it holds the real project.
- **`am start -n com.fadcam.beta/com.fadcam.SplashActivity`, NEVER `monkey`** (it calls
  `thawRotation()` and kills JoyRaptor's rotation lock).
- Back up `project.json` device-locally and restore with `run-as cp` — **never `adb push` onto it**
  (a failed push truncates it).
- **`export MSYS_NO_PATHCONV=1`** before `adb shell /storage/...` — but it breaks the harness
  scripts' `mktemp`. Run harnesses in a clean shell.
- **NEVER build while an export is running.**
- **`strings` is not installed.** Dex-scan with `grep -alc`, ALWAYS with a negative control — that
  is what caught a scan silently measuring nothing.
- **Exporting bumps `lastModified` and RE-SORTS the project list.** Identify projects by the logcat
  `Editor loaded saved project:` line, never by row position.
- **Live-writing dialogs need `setOnDismissListener` AND a save on revert** — BACK bypasses the
  button, and the 3s autosave debounce means a cancelled edit is often already on disk.
- **Verify a claim about a build by comparing binaries, not timestamps.** I told JoyRaptor his phone had
  a bug based on install time vs commit time; `md5sum` on the device APK vs the local one showed it
  already had the fix. One command would have prevented a false alarm.
