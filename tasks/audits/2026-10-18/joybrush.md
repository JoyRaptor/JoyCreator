## Priority findings

### 1. [P1] Give each new drawing a unique persistent document identity before mirroring it

**Location:** `C:/+Projects/Screenrecorder/FadCam/joybrush/androidkit/src/main/kotlin/cc/joycreator/joybrush/androidkit/JbCanvasView.kt:2262–2263`, `2843–2846`; consumer: `C:/+Projects/Screenrecorder/FadCam/joybrush-android/src/main/kotlin/cc/joycreator/joybrush/android/library/DrawingLibrary.kt:378–389`.

**Trigger:** Choose a Joy Creator folder, create drawing A, paint/save, then create a separate drawing B and paint/save. `DrawingLibrary.create()` creates a new *filename and index entry* but no new document ID. The first snapshot of either fresh canvas calls `DocOps.newDocument(DOC_ID, ...)`, where `DOC_ID` is always `"joy-brush"`.

**Impact:** B's first mirror has no remembered folder path. `mirrorFile()` scans existing drawings by document ID, finds A, and atomically replaces A's external archive with B's bytes. Both local library entries can then point at the same external file and alternate overwriting it. Local working copies initially survive, which can hide that the separate external backup has been destroyed. On restoring a folder, `syncFromFolder()` also treats every subsequent drawing with this ID as already known (`DrawingLibrary.kt:295–298`), hiding otherwise distinct drawings.

**Root cause:** The one-canvas constant identity outlived the introduction of a multiple-drawing library. Filesystem uniqueness is not document identity uniqueness.

**Fix:** Allocate a UUID once for each new library drawing, carry it into the initial canvas document, retain it through snapshots, and preserve imported identity only when continuing that document. Migrate existing collisions using distinct working-file identities without overwriting existing external copies. Until collisions are resolved, a matching ID alone cannot authorize adopting and replacing another entry's folder path. Add an end-to-end create-A/save/create-B/save test with a fake JoyFolder filesystem, asserting two independent external files and restoration of both.

**Evidence:** A targeted Python counterexample, tied to assertions against the exact current source strings, reproduced two local drawings resolving to one external path; final external pixels were B. This was a CPU model of the resolver, not actual Android folder writes. The identity and resolver code also remain in unmerged `C:/Temp/jb-integration-1018` at `91dcdc0e1`.

### 2. [P1] Retire the old media window before replacing a document

**Location:** `C:/+Projects/Screenrecorder/FadCam/joybrush/androidkit/src/main/kotlin/cc/joycreator/joybrush/androidkit/JbCanvasView.kt:2027–2040`.

**Trigger:** Paint a wet wash on A, lift the pen, then use **Open…** to load B into the same drawing screen while water is still active. Use drawings with the standard first layer (`layer-1`); that is the normal fresh-drawing configuration. Saving a copy and reopening it in the same screen also exercises the same ownership boundary.

**Impact:** A's working full-float media state survives the document replacement. In the next frame, the old wash can write its look and media payload into B. With a dry pencil/oil window, the next stroke at the same layer/plane/location can reuse stale state because `MediaWindow.place()` considers its old placement already valid.

**Root cause:** `load()` resets the `GlPaintEngine`, uploads B, and loads B's line state, but never resets/releases `mediaCanvas`. It is a separate object holding a separate `MediaLayerEngine` and `MediaWindow`. `GlPaintEngine.resetDocument()` does not notify or reset them. Immediately after queued load work, the render loop calls `mediaCanvas.frame()` (`JbCanvasView.kt:938–943`). If old water is active it runs `wetFrame()` and flushes (`.../gl/media/MediaCanvas.kt:200–204`). The only stale-owner check in `MediaWindow.flush()` is whether its layer ID still exists (`.../gl/media/MediaWindow.kt:125–130`); B's `layer-1` passes. `writeLook()` obtains writable tiles in the *new* engine and blits the old look into them (`MediaWindow.kt:157–163`). No document identity/epoch participates in this validation.

**Fix:** On the GL thread, finish/preserve the old drawing through the established save boundary, then discard its media window before resetting any layer stores. `mediaCanvas.release()` discards the transient engine rather than flushing into newly installed owners; it must run while its own GL context is valid. Bind future windows to a document generation as well as layer and cel IDs, so stale queued work cannot cross documents. Add wet-A→load-B→one-frame and dry-A→load-B→same-location-stroke tests against the real GPU path; assert B's pixels and media payload are untouched by A. Extend the same audit to flatten/delete/undo that removes media ownership while preserving layer identity.

**Evidence:** Source assertions verified that the entire `load()` body contains `engine.resetDocument()` but no `mediaCanvas` call, and traced the next-frame write path and identity guard. A CPU identity/write model demonstrated the collision; actual GPU reproduction is pending. The same load omission remains in unmerged `C:/Temp/jb-integration-1018`. A newly introduced UUID document alone will not solve it: the media window currently never checks document ID.

### 3. [P1] Preserve all-zero mask tiles in the initial-canvas save path

**Location:** `C:/+Projects/Screenrecorder/FadCam/joybrush/androidkit/src/main/kotlin/cc/joycreator/joybrush/androidkit/JbCanvasView.kt:2243–2251`, specifically line 2248.

**Trigger:** On a fresh drawing before a board document has been materialized, add a mask and fully erase an entire mask tile with a sufficiently large, hard, full-opacity eraser. Save and reopen, or create the first board document after masking. Adding a mask when `boardDocument` is null does not itself materialize a board document, so the older save path remains reachable.

**Impact:** The fully hidden 256×256 area reappears. The save succeeds and permanently omits that portion of the mask. Opening Boards or starting the first media/line operation can also materialize metadata using this same readback and lose the mask coverage.

**Root cause:** Transparent paint and a zero mask have different absence semantics. The legacy mask loop skips `Tiles.isBlank(bytes)`. The commit shader's eraser is `dst * (1 - a)` (`C:/+Projects/Screenrecorder/FadCam/joybrush/shaders/jb_commit.frag:48`), so full erasure produces zeros. But an absent mask tile means *white/full coverage* (`.../gl/GlPaintEngine.kt:825`), not black/hidden. `BoardSnapshot.capture()` already handles this correctly by skipping blank tiles only when `!mask` (`.../io/BoardSnapshot.kt:46–47`), with an existing regression test `blankMaskIsRetainedWhileBlankPaintIsOmitted` (`.../src/test/kotlin/cc/joycreator/joybrush/androidkit/io/BoardSnapshotTest.kt:36–41`). That test does not exercise the legacy View path.

**Fix:** Keep zero mask tiles in this loop, or route both initial and materialized documents through the same mask-aware snapshot implementation. Add coverage for fresh canvas→mask full erase→snapshot→archive round trip, plus fresh canvas→mask→materialize board.

**Evidence:** Targeted shader-math/serialization model generated a full all-zero mask tile, applied the legacy skip predicate, then the engine's missing-mask default: coverage changed from 0 to 255. Source confirms the correct BoardSnapshot path differs. No GPU execution was claimed. The skip also remains at line 2303 in unmerged `C:/Temp/jb-integration-1018`.

## Performance finding

### [P2] Stop scheduling settled water and decouple simulation time from render frequency

**Locations:** `C:/+Projects/Screenrecorder/FadCam/joybrush/androidkit/src/main/kotlin/cc/joycreator/joybrush/androidkit/gl/media/MediaCanvas.kt:200–205`; `.../gl/media/MediaLayerEngine.kt:738–746`, `776–780`, `829–830`; `C:/+Projects/Screenrecorder/FadCam/joybrush/core/src/commonMain/kotlin/cc/joycreator/joybrush/core/media/Wet.kt:23`.

One drawn frame always executes four steps at dt=1/120 s. Water's simulated speed therefore follows device FPS. At 60 fps it ages 2 simulated seconds per wall second; at 10 fps, only one third of a simulated second. Idle water remains active until `wetIdle > 240` simulated seconds or another operation releases/stops it. There is no GPU activity reduction that shrinks/clears `wetRect` once actual water settles; `touch(rect)` also dirties the whole wet rectangle for look rendering and persistence. The frame loop requests another render while this flag remains set.

At the defaults this is about 7,201 frames after the last input: roughly 120 wall seconds at 60 fps, 240 at 30 fps, or 720 at 10 fps if the window remains active. These are arithmetic consequences of the loop, not measured temperatures or proof that every wash consumes the full bound. Natural settling does not itself clear the CPU flag. This creates a long GPU/battery tail and device-dependent paint behavior.

This was already recognized in `C:/+Projects/Screenrecorder/FadCam/tasks/joybrush/reviews/MEDIA_PERF_20261011.md`; it remains present in reviewed main. Fix through conservative activity detection, quiet connected-component retirement, fixed bounded simulation ticks and rendering cadence, keeping dt stable. Do not simply enlarge dt: the existing October 12 Note 9 comparison in that report found 2-step and 1-step modes with enlarged dt numerically unstable. The owner-approved direction is immediate brush feedback with water allowed to lag; it still requires bounded backlog and explicit aging semantics.

## High-leverage optimization sequence

The following are candidates for large gains, not a promised 10× speedup. Existing optimizations must be kept in the baseline: current oil already has the oriented footprint scissor (`MediaLayerEngine.kt:647–675`), wet p0/p1 already ping-pongs by step parity, and uniforms already use a reusable bank. Reimplementing those would double-count historical gains.

1. **Reduce actual wet work first.** Conservative per-tile GPU activity reduction with asynchronous readback, connected-component sleep and halo-aware dirty sets replaces a growing bounding rectangle over dry paper. Never use a synchronous `glReadPixels` every frame. Preserve wet connections and sufficient read halos across active/inactive boundaries. Benchmark active versus scheduled area, GPU flux/update time, look time, idle tail, and identical final pixels on tiny sparse drips and broad connected washes. A sparse wash with <10% actual active area is a credible place to seek order-of-magnitude work reduction; a fully wet sheet will not have that saving.
2. **Separate immediate brush presentation from water catch-up.** Keep dt=1/120, a bounded queue and explicit input timestamps. Budget water work per frame, prioritize fresh contact, schedule older components at a lower look cadence, and prevent unbounded catch-up when a phone throttles. Compare owner-visible Option A side-by-side with current behavior using identical sampled strokes. Measure p50/p95 input-to-visible paint, simulation lag and backlog, and final-state quality. Any time-semantics change needs artistic acceptance, not only timing tests.
3. **Remove unconditional impasto look cost for watercolor.** `MediaLook` defaults impasto to 1.4 and the window selects a 53 px look halo when enabled (`MediaCanvas.kt:334`), even though wet-only material does not require oil relief. Classify required channels/relief from actual material state and select an exact flat look where equivalent. Preserve oil-under-water cases and shadow dependencies. Measure look fragment count and GPU time separately, with raw-pixel parity fixtures and deliberately wrong controls. Avoid claiming a smaller halo is correct for mixed media without proof.
4. **Finish atlas residency/temporal admission, then optimize whole-board drawing.** Bounded resident pages reduce costly window reloads and edge truncation, but tile-by-tile dispatch can increase draw calls; compare tile occupancy, upload/write-back bytes, residency churn and shader batch counts. Large Tile/onion previews currently render at board resolution (`GlPaintEngine.kt:4980–4989`) regardless of the visible size; viewport-aware previews and caches can reduce excessive offscreen work. Validate rotated/zoomed views, crop edges and export independently.
5. **Bound save and edit peaks.** Current save reads every tile/media store into CPU arrays before compression, while existing GPU/Undo owners remain resident. Track peak Java/native/GPU memory and readback stall during large drawings, plus line-edit replay units. Future incremental archive writing should use an immutable/versioned snapshot and bounded worker buffers; it must not serialize live mutable textures while water continues. Share/refcount immutable owners or stage per-generation copy-on-write rather than sacrificing atomic save/undo semantics.
