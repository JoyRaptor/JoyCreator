# Codex audit rounds 1 and 2: who fixes what (orchestrator, 11-15 evening)

The owner had Codex audit the code read-only: [round 1](JoyCreator_Audit_Round1_20261115.md) (27 new and 5 known)
and [round 2](JoyCreator_Audit_Round2_20261115.md) (15 new and 2 leads). **Codex read a snapshot from the morning of
11-15 (`65cbae3`), and much has changed since.** So every lane first checks each finding against the current
`joy-creator`, then marks it fixed-already, real (and fixes it) or not-a-bug, with one line of proof on this page.
Lost-work rows first. Codex ran nothing on a device, so a fix needs a test or a device check, as usual.

| R2-TIME-01 | real, fixed (Studio polish lane, 11-15) | Still in the current code. Codex's counterexample committed 3000 ms, overlapping the second neighbour. The lock-only step-past now keeps stepping until the whole object fits (`ObjectTimeScrubSession.flushPastForward`). `tools/jvm-harness/run-objtime.sh`: Codex's case, touching neighbours, a tight cluster crossed by shuttle ticks (no preview overlaps), an exact-fit gap and backward. 3 tests failed before the fix and pass after. Going left has no step-past by design; the mover's lock is already legal there. Not checked on a device. |
| JB-ANIM-01 | real, fixed (JoyBrush screens lane, 11-15) | Still in the current code: each frame was rounded on its own (`AnimExportPlan.build`), and again to hundredths in the GIF. A plan's delays are now differences of boundaries rounded once each, and board GIFs go through the new `core/export/GifTiming` (running totals in hundredths; above 50 a second a drawing shorter than 2 cs is left out, its time given to the one before, and the artist told in a sentence). 30 one-tick frames at 30 fps: PNG 1000 ms (was 990), GIF 100 cs (was 90); 24 fps 1000 ms / 100 cs; 60 fps GIF 100 cs (was 120). `GifTimingTest`, `AnimExportPlanTest`, androidkit `AnimExportTest` (now checks the running-total rule). Cloud: jb-core 3008, jb-androidkit 1353, jb-android 605, all pass. Not checked on a device. |
| JB-ANIM-02 | real, fixed (JoyBrush screens lane, 11-15) | Still in the current code: an ordinary hold was one GIF frame, clamped at 65 535 cs. `GifTiming` writes a longer hold as the same picture again in pieces of at most 65 535 cs, never leaving a piece under 2 cs (the scene export's rule). 999 ticks at 1 fps: 99 900 cs in two pieces (was 65 535). `GifTimingTest.aLongHoldIsWrittenWholeNotCut`. Not checked on a device. |
| JB-ANIM-03 | real, fixed (JoyBrush screens lane, 11-15) | Still in the current code: `requestArt` asked for every frame across the board's projected width, so a zoomed board with more frames there than the 8 MiB cache holds (about 327) kept evicting and re-asking. Now the strip is cut to the screen turned back by the canvas rotation (`core/chrome/FrameStripWindow`) plus a quarter screen each side, a board above or below the screen asks for none, and demand is capped at half the cache. A 64 000 px board with 400 frames: about 19 frames asked for, then nothing more (`BoardRuntimeControllerTest.aWideZoomedBoardAsksOnlyForFramesOnScreenAndThenRests`, `FrameStripWindowTest` incl. quarter and 45° turns). Not measured on a device. |
| R2-TIME-02 | real, fixed (Studio polish lane, 11-15) | Still in the current code: end cap 950 with snap 100 gave 1000. Now clamped again after rounding. `run-objtime.sh`: a jump and a shuttle to an unaligned end cap, a half-step tie, zero, and a neighbour at the cap. 2 tests failed before the fix and pass after. The suite is now in `run-studio-all.sh` (it ran in no suite before). |
| R2-FX-01 | real, fixed (Studio export and audio lane, 11-15) | Still in the current code: `GlPipFrameOverlay` sized every unmasked PiP as 30% of the frame on each side, whatever the clip's shape. Now the editor's fit rule, shared by the editor and both export paths (`model/PipPlacement`); rotation is done in pixels (the old NDC rotation skewed on a 16:9 frame), and the GPU store is y-down like the Canvas bitmaps the compositor reads. `run-pip.sh` (`PipExportTest`): portrait over landscape, landscape over portrait, square, unknown size, corners, 90 and 30 degree turns; NEGCTRLs show the old size, the old centre (mirrored) and the old rotation fail the same checks. Device: see the STATE row. |
| R2-FX-02 | real, fixed (same lane) | Still in the current code: `SurfaceFrameReader.updateTo` decoded a new frame for every output frame. It now keeps the frame it holds when that frame already answers the request (`export/DecodedFrameCursor`, the rule the CPU reader always had). `PipExportTest`: 24 into 30 fps uses about 24 source frames a second and is never more than one source frame ahead; NEGCTRL: the old rule uses 30 and runs ahead. |
| R2-FX-03 | real, fixed (same lane) | Still in the current code: the staging shader wrote straight colour, and `BlendModeGlEffect` divides by alpha. It now writes premultiplied colour, with blending and culling off while it draws. Shader only: no JVM check is possible; the phone check is the brightness of a 50% PiP over grey. |
| R2-FX-04 | real, fixed (same lane) | Still in the current code: `BlendModeGlEffect` and `ImageBlendGlEffect` resolved effect keys at the presentation time alone. Both now use `TimeMap.chunkToEditorMs`, the clock their placement already used. `PipExportTest` checks the arithmetic and that every `resolveAt` in both files goes through it (fails on the old source). |
| R2-AUD-01 | real, fixed (same lane) | Still in the current code. `VolumeAudioProcessor` now multiplies each channel's pan gain by one per-frame gain (volume, or volume x the curve). `run-stereo.sh` (`StereoGainTest`): run against the OLD code in the cloud it failed 7 checks (stereo at full level half way through a fade, 10000 where 5000 was due; 5.1 threw on channel 2), [run 43799938098](https://github.com/JoyRaptor/JoyCreator/actions/runs/43799938098); all pass after. |
| R2-AUD-02 | real, fixed (same lane) | Still in the current code: `AudioClipPreviewPlayer.setVolume` dropped the editor's effective level, and a clip muted at load got an empty chain. Now a player gate (`compositor/PreviewMuteGate`) and a preview chain that always mounts the level processor (`AudioFxChainFactory.buildPreviewLaneChain`; export unchanged). The editor already sends the effective level on every mute toggle, so the editor activity is untouched. `PreviewAudioTest` checks the gate and both chains. |
| R2-AUD-03 | real, fixed (same lane) | Still in the current code (two gains for any layout but mono). One pan gain per channel now; pan moves the front pair, the rest keep unity. `StereoGainTest`: 3, 6 channels, 5.1 panned right (failed before: index 2 out of bounds). |
| W1 | real, fixed (same lane); worse than reported | Media3 flushes a sink's processors on every seek AND whenever the playback speed changes (`DefaultAudioSink.applyAudioProcessorPlaybackParametersAndSkipSilence` calls `setupAudioProcessors`), and the preview's drift correction nudges the speed during play. Each flush put the curve back to the clip's first millisecond. `compositor/PreviewStreamClock` reads buffer times through a forwarding sink and tells the processor where it resumed. `PreviewAudioTest`: a seek to 500 ms reads the fade at 500 ms, a speed nudge at 800 ms keeps 800 ms, export without a clock is unchanged. |
| W2 | not a bug (policy); limit recorded | Export lays a lane's clips one after another: when back-to-back sound clips span a transition, the later clip starts where the earlier one ends rather than where its picture moved to, so the run plays continuously, as it does in the editor. The cost: such a run drifts late against the picture by the transition time swallowed since the last gap (any gap at least that long puts it back). Cutting the earlier clip short instead would clip a song's ending; left as is. Belongs with STU-5's editor-side clock work if the owner wants clip-aligned sound. |
| ENG-01 | real, fixed (Engine Fable, 11-15) | Still in the current code: `WetSheet.begin` took `Was.Lost` as the stroke's way back and a cancel put it back as an empty sheet. Now a stroke whose rollback copy cannot be made first lets the older undo copies go and tries again; if that fails the wash sets into the layer and the stroke starts on an empty sheet; a state that is not kept is never put back as empty. Note 9, bench case `wetSheetFailureProbe` (failure injected on the real engine): of 83,098 wash pixels 277 differ after the cancel (the wash dried a little early; 0.3%), 2 stray; the control without a failure loses 0. The old loss was confirmed by reading, not reproduced on the old build. |
| ENG-02 | real, fixed (Engine Fable, 11-15) | Still in the current code: the undo log moved, then `WetSheet.restore` released the engine and could fail to make the other one. Now the log asks the sheet BEFORE it moves, for undo and (new) redo (`GlPaintEngine.sheetUndoBlocked` / `sheetRedoBlocked` -> `WetSheet.History.ready`): the copy of the sheet as it is and the engine the other state needs (made, or woken) are done then, and a failure leaves everything as it was; a print that goes back with its stroke is checked together with it. Same probe, view turned between strokes: undo and redo with no memory for the other engine both answer "no" with 0 pixels changed, and go through once memory is back (0 to 464 of about 159,000 pixels differ from the first pass). Not covered: both the new engine AND remaking the old one failing while the sheet holds a wash (then the wash is gone from the sheet, said in the log); a wash always sets before the sheet changes shape, so I know no way to reach that. |
| R2-JB-02 | real, fixed (Engine Fable, 11-15) | Still in the current code: `applyBoardChange` called `beforeLayerWrite(null)` first thing. It now asks `core/doc/BoardChangePaint.writes`: the wash sets only when the edit moves, copies, clears or drops pixels, duplicates a frame, or changes where a layer's frames lie or which shows; in doubt it sets. `BoardChangePaintTest` (rename, lock, hold: stays wet; another frame, a moved board, pixel moves, a new frame, unknown layer or preview: sets). Not checked on a phone by eye. |
| ENG-04 | real, fixed (Bug-hunt Fable, 11-15) | Still in the current code: `MediaLayerEngine.allocate` and the brush block made textures inside expressions assigned only on success, `release` threw on the unset `state` before deleting anything, and `MediaTex.fbo` kept an incomplete framebuffer's name. Now a group is owned only once all of it was made (`allOrNothing`), `release` works after a failed start, the framebuffer is deleted with its failure. Fold and Note 9, bench case `mediaFailureProbe`, field `startFailure` (new `MediaInitFailureProbe`, failure injected in `MediaTex`): each of a start's 18 acquisitions failed in turn, 0 textures and 0 framebuffers left, release never threw; a wake that fails then a release leaves nothing and kills none of 16 bystander textures. Limit: the probe was not run against the old code, and it counts only what `MediaTex` makes. |
| ENG-05 | real, fixed (Bug-hunt Fable, 11-15) | Still in the current code: `BrushPreviewRenderer.mediaEngine` caught `IllegalStateException`, which `GraphicsMemoryException` is, and set `mediaUnsupported`. The memory failure is caught first now: that preview stays empty, the next tries again. Builds; read only, no test and not tried on a phone (it needs the memory to run out while the drawer opens). |
| ENG-03 | real, fixed (Bug-hunt Fable, 11-15) | Still in the current code: the queued `mediaCanvas.begin` read the field `mediaSymmetry`, which `finishMediaStroke` clears on the input thread. The guide is read on the input thread before the command is queued. Builds; read only, no test and not tried on a phone (needs a held-up GL queue). |
| R2-JB-01 | real, fixed (Bug-hunt Fable, 11-15) | Still in the current code: `JbCanvasView.duplicateLayer` showed the new stack, then the engine's refusal left the frame's command queue uncaught (the GL thread, so the app). The command now catches it, puts the shown stack back when nothing else changed it and says "There was not enough memory to copy that layer.
