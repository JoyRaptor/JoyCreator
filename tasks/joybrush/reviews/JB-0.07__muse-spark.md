## Finding 1 (Medium): `GlPaintEngine.init()` never clears layers/undo/pools — after a GL context loss, stale texture names are rebound as if they were the user's tiles
Proof: `GlPaintEngine.kt:84-130` (`init`) re-creates programs/buffers/FBO and the 1×1 `clearTex`, but never touches `layers`, `undo`, `strokeTiles`, `freeLayerTex`, `freeStrokeTex`. The kdoc admits "content is lost then" (`:83`), yet the maps still hold dead names. On rebinding, deleted names instantiate as fresh incomplete textures (black), and worse, `newLayerTile`/`newStrokeTile` recycle pooled dead names *without* re-specifying storage (`:352-362`), while `undo`/`redo` (`:253-263` + `put :343-346`) keep swapping them as "before/after". Net: after a loss the user sees black blocks presented as their painting, with a lying undo history — worse than blank. `preserveEGLContextOnPause = true` (`JbCanvasView.kt:77`) narrows but does not close the window (eviction still possible on the Note 9). Fix: clear `layers`, `undo`, pools, and stroke state in `init()` (fresh-document semantics the kdoc already promises).

## Finding 2 (Medium): `DabPlacer` calls `radiusOf` twice per dab and documents stateful-looking lambdas — a double-count trap for JB-1.04 (confirms JB-0.03 Q6)
Proof: `DabPlacer.kt:49-50` — `dabAt(m)` evaluates `radiusOf(s)` (inside `:58-61`), then `step(m)` evaluates `radiusOf(s)` again (`:56`); first sample also pays `step(s)` (`:40`). The kdoc (`:15-17`) invites the brush to "decide size per sample", i.e. exactly the stateful distance/RNG counters Q6 warns about — which will double-advance. Today's `JbCanvasView` lambdas are pure (`JbCanvasView.kt:139-145`), so nothing misfires yet. Fragile twin: `angleOf` (= `tracker.update`, stateful!) is currently called exactly once per dab by accident of shape — only `dabAt` calls it. A future edit that reads the angle inside `step` would double-advance the tip. Recommend JB-1.05 evaluate each lambda once per dab and pass the triple down (the Q6 author's proposal), and assert call counts in a test.

## Finding 3 (Medium): `DabPlacer.lerp` does not interpolate azimuth — lean snaps between dabs
Proof: `DabPlacer.kt:63-72` — x/y/time/pressure/tilt are interpolated; `azimuth = b.azimuth` (`:69`) is snapped, while the sibling pipeline interpolates it wrap-aware (`StrokeSmoother.push`, `StrokeSmoother.kt:139`, via `Angles.lerp`). On fast strokes (sparse samples, long dab gaps) with a leaning pen, the `lean`/`attack` dynamics inputs (JB-0.03) step instead of sweeping, spiking size/flow at dab boundaries — and the tilt-aimed grain plane (JB-1.02) will inherit the steps when wired. One-line fix: `Angles.lerp(a.azimuth, b.azimuth, t)` (it is NaN-safe by construction).

## Finding 4 (Low): negative/NaN dab radii are silently dropped (CPU and GPU agree, both say nothing)
Proof: `TipMath.extent` (`TipMath.kt:68`) goes ≤ 0 for radius < ≈−1.42; then `Tiles.touchedBy` (`Tiles.kt:18-27`) yields an empty range (`x0 > x1`, `for` over empty) and `RefCanvas.stamp` (`RefCanvas.kt:68-70`) iterates nothing — GPU path identically buckets nothing (`GlPaintEngine.addDabs`, `:202`). Consistent (parity kept), but silent: `Dynamics.eval` is unclamped and add-combine can drive size negative, so a brush can make paint vanish without a single error. Belongs with the JB-0.03 Finding 1 ruling (finite/clamped size); noting here so JB-1.05 also asserts `radius > 0` at the boundary.

## Finding 5 (Low): finger is dead forever after the first pen event (documented, owner-ruled — flagging the strand risk)
Proof: `JbCanvasView.kt:110-113` — `penSeen` latches permanently; no reset except view recreation. Documented in the class kdoc (`:28-31`) as the owner's ruling, and palm handling (`PALM_GRACE_MS`, hover, second-finger-cancel `:126`) is otherwise careful and correct. Risk accepted knowingly, but while Phase 2's tool-finger does not exist, a dead-pen-battery user cannot draw at all. Suggest a Lead-visible note, not a code change.
