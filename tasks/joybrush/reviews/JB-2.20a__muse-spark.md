## Finding 1 (BLOCKER): the enum append breaks `:androidkit` compilation — `OraExport` is non-exhaustive, so the whole androidkit module (and every test in it) is red
Proof: clean-worktree build output — `e: …/androidkit/…/io/OraExport.kt:455:56 'when' expression must be exhaustive. Add the 'DIFFERENCE', 'COLOR', … branches or an 'else' branch.` `OraExport.compositeOp` is an exhaustive `when (mode)` over 8 branches with no `else` (deliberately "BY NAME … so a ninth blend mode cannot be added without a compiler error here" — the guard worked exactly as designed, and the 19 new modes tripped it). The enum append landed without touching `androidkit`, so NOTHING in androidkit compiles: not the writer, not `JbArchiveTest`/`OraExportTest`/`PngWriterTest`. Companion runtime break even after compilation is restored: `OraExportTest` asserts `entries.size == 8`, now 27 — and restoring it needs a product decision the spec never makes (which `svg:composite-op` do the 19 map to, or are they refused at export?). `Blend.term` (has `else -> 0f`) and `needsWholePixelBlend` (has `else -> true`) were protected; `OraExport` was not. Fix needs the Lead's export mapping ruling + the `else`-or-19-branches edit in `androidkit` (outside this spec's owner area — which is exactly why it was missed).

## Finding 2 (MAJOR): the "ordinal IS the Studio's modeCode" contract doc is false
Proof: `DocModel.kt:106-110` claims modes are "appended in the Studio's `BlendModes.ALL` order so that a mode's ordinal IS the Studio's `modeCode`" — but `ERASE_BELOW` sits at ordinal 7, so `DIFFERENCE` is ordinal 8 while `studioCodeOf("DIFFERENCE") == 5` (`BlendRgb.kt:83`), `DARKEN` ordinal 5 vs code 7, etc. (repeated at `EnumFreezeTest.kt:61`). No live miscomposite today — nothing in `commonMain` reads `.ordinal` on `BlendMode` (name-based `codeOf`), and the real correspondence is carried by `STUDIO_MODES`/`NAMES`, generator-pinned — but a frozen-contract comment that misstates the invariant will bite the first reader who trusts it (e.g. persisting ordinals, indexing the golden table by ordinal). One-paragraph doc fix stating ordinals deliberately diverge at `ERASE_BELOW`.

## Finding 3 (MINOR): "twenty non-separable modes" comments describe the prescribed design, not the implemented one
Proof: `Blend.kt:74, 92-96, 135-139, 160-163` assert twenty non-separable modes and "`term` answers only the seven SEPARABLE modes" — but only 6 of the 20 whole-pixel-routed modes are genuinely non-separable; 14 separable modes (`DIFFERENCE`, dodges/burns, hard/soft/vivid/linear lights, pin, hard-mix, exclusion, subtract, divide) take the whole-pixel path (proven separable by the identity test's own per-channel list). Functionally identical for in-renderer inputs (packed triple through the same composite), and Q2's prescribed design (seven stay in `term` via one-liner; only non-separables get the `apply`-level call) was NOT what was built — the comments assert the latter. A future reader trusting them mis-reasons about `term` coverage. Fix the three KDoc blocks + rule whether the as-built routing is accepted.

## Finding 4 (MINOR): parity tolerance is relaxed for out-of-range rows vs the spec's flat 1e-6
Proof: `BlendParityTest.kt:290` uses `1e-6 · max(1, |expected|)` — exactly 1e-6 in range (as Decision 5 requires), looser out of range (9e-6 at value 9). Justified by float-ulp scaling (rationale in-file), strict-reading deviation from "within 1e-6". Low severity; record the relaxation in the spec sentence.

## Finding 5 (MINOR): `wholePixelTerm` ignores its `out` parameter + undocumented single-thread assumption
Proof: `Blend.kt:112-121` takes `out` but writes/returns shared `B_TERM` (caller passes `out` at `:78` — signature lies); the path depends on object-level mutable `STRAIGHT_B/STRAIGHT_S/B_TERM/SCRATCH` (`:189-191`) justified only by "apply is not re-entrant" (`:108-110`) — an undocumented single-thread assumption on the export/render path. Works today; races the day `apply` is ever called off one thread.

## Finding 6 (MINOR): `--check` masks a simultaneous Java+GLSL drift
Proof: `gen_blend_golden.sh:82-94` runs the GLSL cross-check only after `cmp` succeeds — on Java drift it exits 1 before the model check, so a simultaneous drift reports only the Java half. Reorder or run both unconditionally.
